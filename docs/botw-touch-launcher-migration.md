## 目标与已确认边界

把旧 `nxnative` 中的 BOTW 触控适配和启动器体验迁到本项目，继续使用 MacNativeGames 的运行时、构建流程和性能实现。尽量保留旧触控代码、数值、手势和菜单判断，只修改它与新项目的连接处。

- 平台：iPhone、iPad、Mac；包括 Mac 启动器和鼠标触控预览。
- 游戏：完整迁移 BOTW 1.9.0。1.6.0 不安排兼容工作，也不刻意删除。
- 游戏范围：BOTW。共用文件需要考虑 TOTK，但本次不扩展 TOTK 触控功能。
- 旧项目的性能优化不迁。帧生成、低内存、渲染调度、缓存策略等使用本项目的实现和默认值。
- 全部非性能功能纳入，包括滤镜/LUT、竖屏、Duo/Seated 分屏、实时符文图标和 HUD 调整；允许为这些功能迁入必需的绘制代码。
- iOS 默认交付三个独立文件：IPA、图形包、RomFS 包。图形资源、基础游戏数据及 DLC 不随 IPA 重复打包，用户在启动器分别导入两类资源。
- 新旧两版并存，使用各自的应用标识与本地数据目录。用户在旧版导出存档和触控布局，再由新版正常导入；不另做旧版扫描、整库搬迁、其他设置导入或自动升级接续。
- 新版自身的跨设备云同步功能纳入。新旧版自动云互通默认不纳入，两版通过已有导出/导入转移存档；这是依据上述数据转移范围采用的方案默认值，不是用户另行确认的云协议要求。
- 用户已授权直接开始执行；本清单继续作为后续实施和 AI 交接的依据。

## 迁移原则

1. 保留旧功能主体，使用少量明确的连接函数接到当前运行时。保留现有 `dm_*` 名称也可以，不做无收益的全局重命名。
2. 先复用目标已有的输入、加载、游戏代码改写和绘制能力。目标缺少的连接点才补上。
3. 独立头文件优先原样复制。混有平台代码、功能代码和性能代码的文件，按函数或改动段迁移。
4. 不整仓合并，不整批 cherry-pick，不用旧 `dm/host` 或 `dm/gfx` 覆盖当前实现。
5. 所有复制文件记录来源提交、旧路径和内容摘要；每处实质修改说明是接口适配还是用户确认的行为差异。
6. 目标工程不依赖 `~/projects/nxnative` 的头文件、库、符号链接或运行产物。迁移完成后，移走旧 checkout 仍应能构建。
7. 沿用已有构建记录、校验和测试机制。无需另建插件框架、通用游戏引擎或复杂的适配框架。

这是逐步接通接口、分块迁移的办法；可以参考 [Branch By Abstraction](https://martinfowler.com/bliki/BranchByAbstraction.html)，本项目只需要实际用到的连接函数。

### M9：资源导入、构建与打包

依赖 M2、M4–M8。

#### iOS 三包交付约定

| 输出 | 内容 | 用户操作与更新规则 |
| --- | --- | --- |
| IPA，例如 `BotW.ipa` | 新运行时、玩家游戏代码的改写模块、启动器、触控界面、小型配置与资源兼容要求 | 作为应用安装。触控或启动器更新且资源兼容要求未变时，只更新 IPA |
| 图形包，例如 `BotW.graphics` | 新项目生成的游戏着色器库、预编译管线、预热清单及其兼容信息 | 在启动器选择“导入图形包”。兼容时继续复用；图形链或相关接口变化后重新生成 |
| RomFS 包，例如 `RomFS.img` | 基础游戏与更新合并后的游戏数据、对应索引与校验信息，以及本次构建选用的全部 DLC | 在启动器选择“导入游戏数据”。游戏版本或数据内容不变时继续复用；DLC 不额外成为第四个包 |

名称为示例，容器内保存新项目生成的数据。沿用旧版的三包使用流程，不以扩展名判断旧编译资源与新运行时兼容。游戏模块及其改写元数据随 IPA 保持一致，图形包与 RomFS 包不装载另一版本的可执行模块。

当前代码的现成能力：`build_app.py --ios-game-data documents` 会把基础 RomFS 镜像放到 IPA 外；`ios/tools/build_ipa.py --image-outside` 也会输出外置的 shader-seed 目录。但图形目录尚未成为启动器可导入的单个图形包，BOTW DLC 仍由打包脚本复制进 IPA。因此，三包是本项必须完成的改动，不能把现有外置选项直接当作三包交付完成。

- [ ] 接通游戏数据与图形资源的状态展示、选择、导入进度、成功/失败反馈和启动前检查。
- [ ] 构建默认输出上述三个独立文件，结束时集中打印各自路径、身份/内容摘要，以及“新生成、复用或跳过”的状态。
- [ ] IPA 不携带已外置的游戏着色器数据、基础 RomFS 或 DLC；随应用编译的通用绘制代码、游戏改写模块与必需清单保留在 IPA。
- [ ] 将目标生成的 shader-seed、设备图形库、管线与相关清单封装成启动器可直接导入的单个图形包；导入和版本管理尽量复用旧 `GraphicsPack` 的流程，只适配新资源布局与兼容规则。
- [ ] RomFS 与 DLC 合为单个用户可导入的资源文件；容器内部保留目标镜像、索引和校验语义，优先复用已有容器能力，不为打包替换整个游戏文件系统后端。
- [ ] 大型镜像不重新压缩；在现有镜像读取能力上接入容器或导入布局。导入结束后只保留一份有效游戏数据；如必须有临时副本，完成发布后清理并正确提示空间需求。
- [ ] 分别校验游戏身份/版本、DLC 内容、图形接口版本、平台/GPU 要求和包内容完整性。支持先导入任意一包，再补齐另一包；两者均满足当前 IPA 要求后才允许开始游戏。
- [ ] 保留原子导入与重复导入识别；导入中断或校验失败时，原有可用资源仍可使用。
- [ ] 迁移旧版仅更新应用的构建能力：可以跳过 RomFS 生成，复用经校验且满足当前图形契约的已发布图形包；仅因 IPA 版本号或触控/启动器修改，不要求重建和重新导入资源。涉及资源契约变化时正确要求更新对应包。
- [ ] 资源导入使用本项目生成的游戏数据与图形资源；不增加旧版运行产物或图形包的跨项目兼容任务。目标格式的身份、版本、完整性和兼容检查继续有效。
